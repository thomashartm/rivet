# ADR-0020: Permission matching rules

- Status: Proposed
- Date: 2026-11-25

## Context

ARCHITECTURE.md §4.7 lists the capabilities and their scopes. It does not say how a request is compared with a grant. The permissions ticket (#7) needs the rules. Part 1 of #7 is on `main` (`crates/rivet-core/src/permissions.rs`). The rows "Secret backends" and "Secret namespace and scheme" and part 2 of the `filesystem` row are not implemented.

## Decision

| Capability | Rule |
| --- | --- |
| `network` | The host must equal a granted host (ASCII case ignored) and the port must be in its list. No wildcard, no subdomain, no name resolution. Two IP addresses are compared as addresses. |
| `filesystem` | A scope is an absolute path or starts with `~`. The scope and the requested path are resolved (symbolic links, `..`) before the comparison. Write access needs a read-write scope. Part 2 of #7: the service opens the file itself, below a directory handle of the scope root, and returns the open handle. It returns no path that a caller opens again. |
| `secrets` | A namespace is the first `/` segments of the path of a secret URI. Exact and case-sensitive. It applies to every secret backend scheme. An entry that contains `://` grants nothing; this form is reserved for a later rule per scheme. |
| Update review | The service stores the capabilities that the installed manifest requested. A new manifest is compared with that request. A network entry is compared with the rule of the `network` row (ASCII case ignored, IP addresses as addresses), so another spelling of the same host is not an addition. A filesystem path and a secret namespace are compared by exact text. If it adds nothing, the grant of the user is kept, also a partial grant, and is cut to what the new manifest still requests. If it adds something, the grant is removed until a new review. |
| Secret backends | An extension registers a backend with itself as owner. It may register a scheme only if its manifest declares the scheme and the user granted it in the install review. The scheme `keychain` is reserved for the core on every platform. The schemes `aws-sm` and `gcp-sm` are reserved for built-in extensions when the signature check can prove the origin (#12). A second registration of a scheme fails with a `policy` error. Not implemented, no code: the manifest declaration and the reserved scheme `keychain` are for #7 part 2 and wait for the decision of the maintainer on the manifest format; the reserved schemes `aws-sm` and `gcp-sm` are for #12 part 2. |
| Secret service | Each extension gets its own secret service. It checks the namespace first and asks the backend only after that. An extension can read through a backend that another extension registered. The service cannot remove a value from the log redaction; only the host can. (#7 part 2, `ExtensionSecrets`, on `main` since PR #132.) |
| Secret namespace and scheme | Open, for the maintainer: bind each namespace to one scheme with a manifest table (`scheme`, `namespace`). Until then a namespace applies to every scheme. |

## Consequences

- Every rule denies in case of doubt.
- A grant for a secret namespace gives access to that namespace in each backend. The install review MUST say this (to enforce in #51; no check exists).
- An update that adds no capability needs no new review (§4.7), also after a partial grant.
- The manifest needs a place to declare secret schemes. This is a manifest format change.
- A swap of a parent directory for a symbolic link after the check cannot redirect an open, when part 2 is done. The crate for directory handles (candidate: `cap-std`) is not chosen; its licence and size are not checked.
- A secret value that an extension already holds stays usable after a revoke. Only the next request is denied. To stop the use, the host must deactivate the extension.
- Path of a secret URI in the check (review finding R-57): a path is denied if it has a `%`, a `\`, a control character, an empty segment, or a segment `.` or `..`. Each other character is compared as text; nothing is decoded or normalised. `%` stays denied because code that handles a URI often decodes it; a secret with `%` in its name cannot be read by an extension (known limit). A secret backend MUST use the path as text.
- A path that is equal to a granted namespace is permitted: `keychain://acme-postgres` with the namespace `acme-postgres`. So a namespace can name one secret.
- Home directory: if it is not absolute or is a filesystem root, the service has no home directory. A scope that starts with `~` then grants nothing, and the service writes one `warn` event when it is created.
- Secret service and backends (review findings R-75 to R-78, on `main` since PR #150; read in `secrets.rs` at commit c2e8865: second grant check, read limit of 30 s, 256 values per owner, scheme names). The rule that the keychain backend has no read limit is on `main` since PR #154:
  - The service checks the grant before it asks the backend and again when the backend has answered. If the grant is gone, the value is dropped and the read is denied. The dropped value stays in the redaction until the owner is released.
  - A read of a backend has a time limit: one constant in `secrets.rs` with the default value of the call limit (30 s, ADR-0021), no new setting. A host import must not wait without end (ADR-0018). After it the read fails with a `retryable` error; the extension is not failed for it. The limit is for backends of extensions only. It depends on the backend, not on the reader: a read by the core of a backend of an extension has the limit too, because the backend is guest code. As built on `main` at commit 9b61096 the limit is on only when an extension reads (`secrets.rs:397`; review finding R-97); the fix is not on `main` on this date. The keychain backend of the core has no limit here, because the OS can ask the user and the user can need more time. Known limit: a keychain read that nobody answers (headless process, locked keychain) waits without end, and a prompt inside a lifecycle call can exceed the call limit of the host.
  - An error text of a backend of an extension is text from a guest: the category stays, the text is redacted, cleaned and cut, and gets a prefix of the host that names the scheme. The source of such an error is dropped (review finding R-99; as built). In `wasm.rs` an error that a guest returns has a message and no source too. A trap of Wasmtime is different: it keeps the error of Wasmtime as source (`wasm.rs`, function `failure`, read at commit 1d0690a); that source is made by the host runtime, but it was not checked that it holds no text of the guest. Reason: the source is made by guest code, has no limit and can hold a secret value before the value is registered for redaction; an error also reaches outputs that do not redact. §5.6 has two rules here, "MUST keep the source chain" and "MUST NOT contain secrets"; for an error of guest code the second rule wins. This narrows the first rule of §5.6, so it is open for the owner; §5.6 is not changed.
  - Redaction: a value from a read is registered for the owner that read it. The values of an owner are removed when the host releases this owner. One owner can have 256 different values. At the limit, a read of a new value is refused with a `policy` error; no value leaves the redaction to make room. This is what the code does (pull request #150). The values stay when a grant is revoked and when the service object of the reader is dropped; only the release of the owner (unload) removes them. So the only recovery at the limit is to unload the extension (review findings R-77 and R-98). The documentation of `ExtensionSecrets` in `secrets.rs` must state the limit, the effect on secrets that rotate and the recovery. When the SDK gets the contract of the secret service (SDK freeze, ticket #5), that documentation must state the same.
  - Open, owner decision: an extension that reads credentials that rotate (for example every 15 minutes) reaches the limit after some days and then fails until it is unloaded. The other option is that the oldest value of this owner leaves the redaction. That option can show a secret that is still valid in a log, so it is not chosen without the owner.
  - Known limit: a read that ends after the release of its owner registers its value again. It stays until the next release of this owner, at most 256 values. This is accepted (review finding R-99): the error is to the side of more redaction, and the value reaches no extension code.
  - A value that is equal to an extension id that the secret code knows (the reader and each owner of a backend) is not registered and the read is refused with a `policy` error. Known limit: an extension that owns a backend can still make the log unreadable for other words, up to its 256 values. The rule is for a value from a backend of an extension. A value of the keychain is always registered, also when it is equal to an id (since PR #154): a secret of the user is never left without redaction.
  - Open, owner decision (review finding R-76, not fixed): the redactor replaces values in the complete log line. So the audit line of a denied access can lose the extension id or another word. Cases that the rule above does not stop: a keychain value that is equal to an id; the id of a loaded extension that the secret code does not know; a value that is equal to a part of an id or to a word of the line (`reader`, `denied`, `WARN`). Proposal of the reviewer: the log writer does not redact named fields that only core code writes (extension id, capability). This takes text out of the redaction (§7.4), so it is not ruled here. Direction if the owner accepts it: the exemption is bound to the type of the value (an `ExtensionId`, a fixed enumeration of the core), not to a field name; text of a guest never gets it (guest text is one field, ADR-0018). Until the decision: the rule above stays, the minimum length of a redacted value stays 4 bytes (ADR-0022), and the code does not exempt a field.
  - The secret service of an extension is made only for a store that has a redactor. Without one it is refused, so no value reaches an extension that the log cannot redact (§7.4).
  - Scheme names, until the manifest declares schemes (open decision): `keychain` cannot be registered by an extension. `aws-sm` and `gcp-sm` can be registered only by an extension whose id starts with the segment `rivet`. Each other scheme must be equal to the publisher segment of the extension, or start with it and `-` or `.` (publisher `acme`: `acme`, `acme-vault`). The origin of a `rivet` extension is not proven at load (ticket #138).
- Capability values are checked when they are granted (review finding R-85, on `main` since PR #156). The SDK has one check for a capability set, the same code that the manifest parser uses. The permission service runs it on each set before it stores a grant and refuses an invalid set with a `user` error. The constructors of the SDK check nothing; a value that code builds is as untrusted as a manifest file.
- A grant is the decision of the user at install or update review (§4.7). The extension host does not revoke it: it stays after deactivate, failure, restart, unload, reload, disable. Only an uninstall or the user revokes it. When an extension stops, the host removes what the extension holds: its secret backends, services, commands and jobs. This differs from one criterion of ticket #7 ("the host revokes grants on unload"); the owner decides.
- The extension host holds the secret store itself. An extension never gets the secret store or the permission service through its context (§7.4).
- A granted host name does not grant its addresses. The caller MUST connect to the host that was checked (to enforce in the network host import, #7 part 2; no check exists).
